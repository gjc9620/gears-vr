# 场景视图集合提交调查

2026-10-12，第一人称 Mod 安装状态，最低设置 / 1080p。此阶段只观察参数，不新增视图、不修改视点、不重复游戏更新。

## 静态线索

Ghidra 中原始 EXE 的 0x1402c78f4 / 0x14026858c 无已定义函数，静态字节与运行时指令不同。因此没有在原项目上强行分析保护后的字节。沿现有运行时读取工具扩展显式入口模式：`--skip-vtables --max-instructions 8000`，使绘制函数 0x2c78f4 的有界直接分支分析完成 2,106 条指令，未触及上限。间接跳转、异常路径和真正函数边界仍可能遗漏。

新候选 RVA 0x3a148c：来自绘制路径 0x2c8904，参数 RDX 是此前传入 LocalPlayer 场景视图构建函数的同一栈上集合。内部读取集合 +0x18，分配 0x140 字节对象，调用 0x116250 构造，再沿不同分支安排执行。用途暂记为“视图集合提交候选”，不是恢复的官方符号。

旧 0x26858c 候选遍历对象和输入视图数组，并读取视图 +0x370 / +0x374 / +0x378 的三维值用于判断。它接收视图集合不等于渲染提交入口，不宜据此添加双眼渲染。

集合构造包装 0x3c42b4 调用 0x115e54；后者初始化 +0 和 +8，写入 +0x10 的 RenderTarget 参数和 +0x18 的 Scene 参数。这支持开头为数组的候选布局，但还需动态验证数组容量与元素。

## 动态调查

新增 `--family-diagnostics` 与其他改写 / GPU 诊断模式互斥。版本哈希、两个相机入口和 0x3a148c 的 11 字节签名均核对后安装普通代码 Hook。参数读取最多四个视图指针，工作线程写 CSV；回调不等待 GPU、不写文件、不改集合。ABI 独立测试通过，检查参数转发、入口恢复、无效容量与不可读指针拒绝。

PID 40888，25 秒：6,641 条场景视图、6,643 条集合候选、6,637 条 Present。候选调用者全部为 0x2c8909，与场景视图同一线程 46884；Present 在另一个线程 48772。Present 失败 0，记录丢弃 20 条，所以不宣称一对一无损对应。没有视点改写。停止后 active=0，五处入口外部独立读取恢复。

首版数组容量上限 16 拒绝全部集合记录，故这一轮没有证明数组元素与 SceneView 相符。现改为记录原始 header，容量允许至 1,024，但实际只读取 count（最多四个指针）。后续 PID 2620 验证实际容量为 17、数量为 1；容量是分配余量，不代表有 17 个视图。

新游戏 PID 28756 在首个 Hook 创建时返回 MH_ERROR_MEMORY_ALLOC，尚未启用任何 Hook，disable_status=0 / active=0。只读 VirtualQuery 检查目标附近约 ±2 GB 找不到适合的空闲分配区。新调查需在游戏启动早期预留近地址跳板，进入关卡核对对象后再开启采样；扩大 rel32 范围不能解决没有空闲区域的问题。

`launch_reserve.py` 在新进程启动阶段只调用 MH_CreateHook，预留三个跳板，不启用 Hook；DLL 内和外部进程分别核对三个入口仍为原字节。进入关卡后，`start_capture.py --use-reserved` 重新定位当前玩家对象、核验版本与入口，再启用有时限的采样。同一 DLL 不支持第二次开始，失败时不自动重复注入。

PID 2620，20 秒：5,413 条场景视图、5,413 条集合提交、5,413 条 Present，丢弃 12 条记录，Present 失败 0。全部集合数组可读且 count=1 / capacity=17；5,411 次提交在同线程、同集合地址的前序场景视图记录中找到完全相同的指针，间隔中位数 0.0315 ms。其余两条保留为未匹配，不能用推测补齐。集合调用者全部为 0x2c8909，线程 35416；Present 线程 45116。没有视点改写，停止 active=0，五处入口独立核对全部恢复。

这证明实际观察的提交路径接收了玩家 SceneView。它不证明视图生命周期、增加第二个视图的安全性、双目画面，或无损一对一 Present 对应。`analyze_family.py` 检查捕获状态、恢复、数组、调用者和超过 99% 的指针对应；证据为 `analysis/runtime/family-2620.{csv,json,status.txt}`、`family-2620-restored.json`、`family-2620-correlation.json`。

独立目录重新编译后，正常退出并重启至 PID 46736。新启动器外部独立核对三个预留入口未改变，通过五个菜单后截图及递增的摄像机时间确认进入关卡。20 秒再次采样：集合 5,271 次，指针对应 5,269 次，全部数组 count=1 / capacity=17，中位间隔 0.0322 ms，丢弃 10 条，Present 失败 0；五处入口均恢复。对象地址与 PID 2620 不同，由定位器重新获取，未复用旧堆地址。证据为 `reserve-46736.json` 与 `family-46736-*`。

## 渲染视图副本线索

PID 2620 只读指令分析：0x116250 共 301 条、0x193d50 共 361 条、0x194454 共 189 条，均未触及分析上限，但间接调用和实际分支覆盖仍未验证。

- 0x116250 调用 0x3a4c54，将输入集合复制到渲染对象 +8；0x3a4cd8 为新指针数组分配内存，再复制 count×8 字节。
- 0x3d4e28 按输入 count 为渲染对象 +0x68 的数组准备空间。0x3dd08c 添加一个步长 0xD30 的元素。
- 0x193d50 接收新元素与原 SceneView，调用 0x194454 复制基类字段并初始化额外渲染状态。0x116250 随后将自己的集合数组元素替换成这个渲染视图，并将视图 +0 写成自身集合地址。
- 0x194454 并非简单 memcpy：除矩阵区间复制外，它遍历 +0x140 的节点、复制多个容器，并对 +0x418 指针关联对象执行原子引用计数递增。因此不能直接按猜测尺寸克隆 SceneView。

以上是运行时指令推断，不是已恢复的官方类型或动态复制验证。下一步应观察副本构造前后及销毁路径，再决定眼间距和非对称投影的接入位置。原始证据：`analysis/native/renderer-constructor-2620.json`、`renderer-view-copy-2620.json`、`scene-view-copy-base-2620.json`。

销毁路径补充：0x15bda4 调用 0x15c27c，后者尾部进入 0x15ca7c，处理 +0x418 关联对象、释放 +0x3ec / +0x380 等容器及 +0x140 节点。0x1753a0 对计数执行原子减一，并在减至零时调用清理函数。这与复制中的引用计数增加相符；仍须动态验证实际对象寿命，不代表可以在任意线程释放。证据：`render-view-destruction-2620.json`、`render-view-destructor-base-2620.json`、`view-state-release-46736.json`。

本地证据：`analysis/native/stereo-render-path-40888.json`、`stereo-submission-candidates-40888.json`、`family-base-constructor-40888.json`、`analysis/runtime/family-40888.{csv,json,status.txt}`、`family-40888-restored.json`。

## 半自动菜单导航

`tools/game-io/menu_continue.py` 使用本机已人工核对的五张 640 × 360 菜单截图，文件 SHA256 与游戏 EXE 版本核验；连续两次匹配 expected state，且与其他模板有足够距离后，才向验证的游戏 HWND 发送回车。检查严格顺序、PID/HWND、1080p 和 F8，未知状态等待后超时，不盲按。

模板配置在 `analysis/game-io/menu-templates.json`，由本机已核对截图建立，不进入 Git。PID 28756 实际启动测试自动通过五个菜单，之后独立截图确认进入关卡。此工具只声明启动加载，关卡是否完成加载仍需独立核对；当前只支持这个版本的英文菜单及本机设置。

PID 46736 启动时游戏窗口最小化，首轮窗口采图明确失败，没有发送回车。导航器现只对已经验证的游戏 HWND 执行恢复，再重新等待连续图像匹配。修复后五步导航实际通过，不依赖全局键盘输入或用户切换焦点。
