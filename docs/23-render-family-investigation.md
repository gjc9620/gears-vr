# 场景视图集合提交调查

2026-10-12，第一人称 Mod 安装状态，最低设置 / 1080p。此阶段只观察参数，不新增视图、不修改视点、不重复游戏更新。

## 静态线索

Ghidra 中原始 EXE 的 0x1402c78f4 / 0x14026858c 无已定义函数，静态字节与运行时指令不同。因此没有在原项目上强行分析保护后的字节。沿现有运行时读取工具扩展显式入口模式：`--skip-vtables --max-instructions 8000`，使绘制函数 0x2c78f4 的有界直接分支分析完成 2,106 条指令，未触及上限。间接跳转、异常路径和真正函数边界仍可能遗漏。

新候选 RVA 0x3a148c：来自绘制路径 0x2c8904，参数 RDX 是此前传入 LocalPlayer 场景视图构建函数的同一栈上集合。内部读取集合 +0x18，分配 0x140 字节对象，调用 0x116250 构造，再沿不同分支安排执行。用途暂记为“视图集合提交候选”，不是恢复的官方符号。

旧 0x26858c 候选遍历对象和输入视图数组，并读取视图 +0x370 / +0x374 / +0x378 的三维值用于判断。它接收视图集合不等于渲染提交入口，不宜据此添加双眼渲染。

集合构造包装 0x3c42b4 调用 0x115e54；后者初始化 +0 和 +8，写入 +0x10 的 RenderTarget 参数和 +0x18 的 Scene 参数。这支持开头为数组的候选布局，但还需动态验证数组容量与元素。

## 动态调查

新增 `--family-diagnostics` 与其他改写 / GPU 诊断模式互斥。版本哈希、两个相机入口和 0x3a148c 的 11 字节签名均核对后安装普通代码 Hook。参数读取最多四个视图指针，工作线程写 CSV；回调不等待 GPU、不写文件、不改集合。ABI 独立测试通过，检查参数转发、入口恢复、无效容量与不可读指针拒绝。

PID 40888，25 秒：6,641 条场景视图、6,643 条集合候选、6,637 条 Present。候选调用者全部为 0x2c8909，与场景视图同一线程 46884；Present 在另一个线程 48772。Present 失败 0，记录丢弃 20 条，所以不宣称一对一无损对应。没有视点改写。停止后 active=0，五处入口外部独立读取恢复。

首版数组容量上限 16 拒绝全部集合记录，故这一轮没有证明数组元素与 SceneView 相符。现改为记录原始 header，容量允许至 1,024，但实际只读取 count（最多四个指针）。修改后的关卡采样尚未成功，不能将容量猜测当作已验证原因。

新游戏 PID 28756 在首个 Hook 创建时返回 MH_ERROR_MEMORY_ALLOC，尚未启用任何 Hook，disable_status=0 / active=0。只读 VirtualQuery 检查目标附近约 ±2 GB 找不到适合的空闲分配区。新调查需在游戏启动早期预留近地址跳板，进入关卡核对对象后再开启采样；扩大 rel32 范围不能解决没有空闲区域的问题。

本地证据：`analysis/native/stereo-render-path-40888.json`、`stereo-submission-candidates-40888.json`、`family-base-constructor-40888.json`、`analysis/runtime/family-40888.{csv,json,status.txt}`、`family-40888-restored.json`。

## 半自动菜单导航

`tools/game-io/menu_continue.py` 使用本机已人工核对的五张 640 × 360 菜单截图，文件 SHA256 与游戏 EXE 版本核验；连续两次匹配 expected state，且与其他模板有足够距离后，才向验证的游戏 HWND 发送回车。检查严格顺序、PID/HWND、1080p 和 F8，未知状态等待后超时，不盲按。

模板配置在 `analysis/game-io/menu-templates.json`，由本机已核对截图建立，不进入 Git。PID 28756 实际启动测试自动通过五个菜单，之后独立截图确认进入关卡。此工具只声明启动加载，关卡是否完成加载仍需独立核对；当前只支持这个版本的英文菜单及本机设置。
