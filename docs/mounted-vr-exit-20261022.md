# 上机枪结束 VR 模式：恢复边界旧姿态帧修复

2026-10-22 用户在正版游戏真机测试中报告，上机枪直接结束 VR 模式。本轮按用户安排使用现场日志、代码和离屏检查，不启动游戏寻找机枪，不操作仍在运行的用户游戏。

## 现场与原因

现场会话为 `continuous-stereo-47932-20261022-030325-dc928d43`，native 为最新默认 CoverAim2，SHA256 `04ff9ff8c1465c2019c78b8b0309275a18c4e7208117fa65e8e00396041b71e0`。世界恢复的 Prepare、Commit 均成功，generation 已到 2，之后发生 `owned_error=19`，会话以 `proof_failure` 结束。

失败的首个新资源帧 ticket 3284 已完成左右眼绘制、提交和场景资源证明，但 GPU 出图回执为 `ticket_invalid`。它携带的头显姿态接收时间比恢复完成记录早 2.551 ms，选择帧的时间则比恢复完成记录晚 5.970 ms。新资源 generation 和帧编号均在恢复后的范围；原保护代码把“合法新帧携带提交前的姿态”和“无效／已退休帧编号”合并为相同拒绝原因。出图调用方将这类拒绝统一升级为错误 19，导致正常的恢复边界时序触发整个 VR 会话退出。

这里的时间差相对于日志中的 commit 完成记录；不将它写成头显黑屏时长或单独的世界截止时间测量。

## 修复

- 原来的姿态截止时间比较保持不变，旧姿态帧仍不提交 GPU 复制或 XR 出图。
- 将“已通过元数据、绑定、图像几何、帧编号和输入来源检查，但姿态早于或等于当前恢复截止时间”的情况单独记录为 `world_sample_stale`。
- GPU 出图调用方允许丢弃该帧并正常退休已完成的证明，继续接收后续新姿态帧。它不再触发错误 19，也不重标记旧帧或给它换用新姿态。
- 已退休编号、坏几何、错误资源绑定、来源改变、API／设备错误仍使用原来的失败路径。共享 GPU packet 布局、版本及 XR 二进制保持不变。

## 恢复流程继续加强：MountedResume2

用户继续要求增强恢复逻辑。本轮仍只修改代码、执行离线检查，没有启动游戏、寻找机枪或操作用户游戏。新增三方面保护：

- 原生切换正式提交时，将同一个姿态截止时间同步交给 `StereoGate`。姿态早于或等于截止时间时，在构造新世界 renderer 之前跳过，且不消耗待执行的回正；第一个有效新姿态负责回正。原来的 session、来源、重放、跟踪和几何检查保留，GPU 出图末端的 `world_sample_stale` 保护也保留。
- 当 native 明确处于 `world_handoff_phase=4`、旧世界已暂停而恢复候选被拒绝时，允许对同一对象身份继续重新采样和严格验证，避免超过普通尝试上限后永久搁置恢复。普通发现／结构错误的尝试上限保持；重试间隔递增并封顶，默认为 2、4、6 秒，持续失败后保持 6 秒，防止重试越来越慢或无间隔循环。该退避只用于失败，不给成功切换增加固定等待。
- `OpenEvent` 暂时不可用或 `SetEvent` 失败时，保留同一份不可变恢复包，以有上限的退避继续发送同一通知。已经成功发送的 Prepare／Commit 即使回执超时也不重发，继续接受严格匹配的迟到回执。进程身份、停止状态、其他请求冲突仍阻止操作。新的恢复任务同时清除上一任务的超时标记，恢复已有的 10 ms 活动事务轮询。

## 相机时间戳跨帧失败后的快速重新采样

复查保存的 2026-10-22 会话日志，仍可见 `AnchorSamplingRejected`、`Cross-frame camera timestamp during identity checks`、五次严格采样均失败的记录。当前代码中，这种尚未发布候选的时间戳暂态失败也会进入普通 2 秒退避；已有完整观察、同一身份的准备连续失败三次时，还可能耗尽普通尝试次数，在相机恢复稳定后继续跳过准备。

新增 `timestamp_guard_retryable()` 只识别实际的 `AnchorSamplingRejected` 类型和完整的最后一次失败 guard：guard 必须未接受，1–5 个尝试必须全部明确失败且标记为可重试，异常类型／原因必须为已知时间戳跨帧，外层原因及最终 guard 原因也必须吻合。成功过但超时、混入硬失败、仅消息相同、诊断摘要可重试、错误类型／结构以及注册表子类都不能触发此策略。

Runtime 仅在只读观察构造或无发布的候选构造调用上产生内部重采样标记。失败先关闭本次读取器或 attestation 租约，owner 丢弃所有部分数据；下一次仍是新读取器和完整证明。发布函数不在标记范围内，已经发布的回执、Prepare／Commit 通知及迟到回执协议不变。

严格匹配的失败前三次计划等待为 50／100／150 ms，之后回到普通退避；它不消耗同一身份的硬失败次数。一次完整成功的观察或准备重置短重试预算，代码／身份／未知错误的原次数限制保留。owner 按到期剩余时间唤醒，并在这次有界准备期间使用已有快速轮询。原严格 guard 的五次／200 ms 上限和所有身份、链接、代码、姿态证明保持，没有接受失败采样。

独立加载保存的旧协调器源码，对同一合成输入比较：一次纯时间戳失败后的计划等待为旧 2 秒、新 50 ms；三次后旧路径为 2／4／6 秒且耗尽尝试，在条件稳定后仍未准备，新路径为 50／100／150 ms，条件稳定后完整准备成功。此结果属于状态机调度验证，不是游戏或头显时间测量。
