# 无延迟上下机枪：继续开发与验证

本轮目标是上下机枪时持续出图，没有额外恢复等待。成功准备的 CPU 时间下降仍不足以证明这个目标，目前不标记目标完成。

## 已实现的进一步改动

- 菜单观察改为单个串行后台工作线程。恢复协调器不等待菜单 RPM；原有采样时间戳、状态分类与发布校验保留，关闭时先收完当前读取，再发布最终 UNKNOWN 并关闭 reader。失败会回传 owner，没有并发复用 reader。
- 已有入口认证只需要核对主程序与 Mod 的两个已封存模块基址。每个认证边界仍重新枚举全部模块基址，但只查询这两个模块的文件名；完整 DLL 摘要、进程身份、模块路径及全部封存跳转字节的前后校验继续执行。
- 恢复配置采用静态证书模式，省去未写入 INI 的位置/旋转诊断样本。保留完整身份、关系、属性、汇编边界及短时间戳校验。此模式必须使用 live entry attestation；正常首次启动仍保留诊断采样。native 接收、提交与逐帧实际姿态验证沿用原实现。元数据明确记录 `pose_sampled=false`、`sample=null`，不把未采集姿态标为成功。
- 定期探测到期时也先尝试廉价指针提示。提示为真时使用一次完整采集；提示为假或读取失败时仍执行完整定期观察，包括同地址身份变化。这样可避免“刚好定期探测到期”导致额外完整观察。提示不授予发布权限。

普通、mounted 的合成内存测试证明静态模式配置及 INI 内容与诊断模式一致；校验内时间戳变化、角色/链接变化仍拒绝证书。后台观察测试覆盖阻塞读取、异常回传、单个在途工作和关闭顺序。模块测试覆盖当前成员关系、缺失/卸载、路径查询失败及 lease 关闭。协调器测试覆盖到期时的单次采集和失败提示的完整观察回退。

## 第一轮实际证据及其限制

`mounted-latency5-async-actual-20261021` 使用当时最新默认 native `ca66cdeac91915be17d30a5b1ff5008ae575acb6f7e60d82ff4ffb6f5f8a18c0`，保留 CopyAllthreadsPrefix、ADS 及既有修复。native-capture 395 项和 resolver 22 项检查通过，共 417 项。

该轮完成 checkpoint 新世界恢复和独立 XR projection 提交。恢复 worker 使用诊断模式，观察 220.0281 ms、准备 874.6083 ms，总计 1094.6364 ms，`single_acquisition=false`。Prepare 到 committed 为 208.8488 ms。后台菜单初始化最大耗时约 3578 ms，但这次证据没有证明后台化已消除约 200 ms 的握手等待，不能据此宣称握手改善。

owner 退出 0，后台 reader 关闭，native 清理、独立 79 项入口还原、正常关闭和五份保护文件还原均通过。然而 `run_stereo_continuous.py`、`start_capture.py` 在这次运行中发生磁盘字节变化，自动源码一致性门使整轮 **`passed=false`**。原始失败报告不改记通过。该证据只用于决定下一步复验，不能作为新默认路径的完整验收。

## 正在进行的固定副本复验

为避免共享源码修改影响归因，复验使用现有离线 staging 工具生成私有、完整的 Python/Native 运行目录，记录源码清单与 SHA256。测试保持最新默认 native/XR，使用认证的置后窗口启动与模拟器，不启用后台物理手柄输入，结束后还原原始设置。等待所有其他 FPS/autoplay 工作者及游戏结束后才生成最终副本、运行检查和测试；不向其他聊天发消息。

固定副本分别运行新路径和诊断/同步菜单控制组；私有 launcher 只记录候选实际采样模式与 INI 摘要，控制组显式标记。新路径还补充只读交替准备测量。默认清单若已升级 native/XR，则拒绝用较旧副本继续测试。

回归前必须证明源码固定，实际候选确实由新模式生成、native 完整验证后成功出图、退出与还原完成。完整目标还需要实际机枪上/下切换的连续出图证据；当前仍缺少这项验收。

原始证据、源码副本和私有测试入口保存在 ignored `analysis/`，不进入发行包。

## 固定副本第三轮结果

`mounted-latency6r3-frozen-fast-actual-20261021` 的新路径完整通过。冻结目录为 `analysis/m6qa3`，保留当时最新默认第一人称预览 native（SHA256 `045ca20af3ec7a97b40320219dbcf9ae99d880008ee3ed53e15c4191a8b49b9d`）及 MountedLatency1 XR。399 项 native-capture Python 检查通过（3 项跳过），另有 22 项 resolver 检查通过。

实际发布候选的独立回执明确记录 `pose_sampled=false`，并与 native 接收的完整 Anchor/UI/Crosshair INI 摘要一致。源码固定、checkpoint 新世界恢复、独立 XR 出图、菜单工作线程关闭、native 清理、79 项入口还原、正常关闭及五份保护文件还原通过。worker 使用一次完整采集，准备 807.0193 ms；Prepare 到 committed 仍为 201.1124 ms。这是 checkpoint 恢复测量，不能写作实际机枪黑屏时间。

同进程只读交替候选的成功准备中位数为诊断姿态模式 718.8685 ms、静态证书模式 602.10905 ms；四份完整 INI 内容相同。重采及总耗时保留在原始报告中，不把成功尝试时间当作端到端等待分布。

同一固定副本的旧路径控制组没有完成启动：诊断姿态采样持续跨帧，最终到达激活前准备期限，native 尚未激活。该轮 `passed=false`，不能拿它与新路径的成功 checkpoint 比较总恢复耗时。保留失败记录，并将后续对照限定为同一已启动进程、相同静态证书模式，只改变单次组装的重复读取策略。

第二轮固定副本还暴露了真实的协调器取消标记问题：上次工作失败后，下一次廉价提示错误地沿用已取消标记，无法进入新完整采集。已将提示读取的存活检查与在途工作的取消令牌分开；新工作仍要等旧工作结束后才重置令牌。两项回归覆盖失败后的重试和仍在途旧工作不可被重新放行；第三轮恢复通过包含此修正。
