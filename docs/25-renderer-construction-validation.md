# 完整渲染对象构造：Mod 与原版对照

2026-10-12。观察玩家视图副本在完整渲染对象构造结束后的归属，不新增视图、不修改镜头，不证明双眼渲染。

## 观察位置

新增 0x116250 四参数、返回指针 Hook，保留原调用语义。仅当线程正在执行已观察的 0x3a148c 集合提交时记录。输入前读取集合与首个视图矩阵；原构造结束后读取：

- 渲染对象 +8 的集合、集合中的最多四个视图指针。
- 对象 +0x68 的连续渲染视图存储数组 header。
- 首个视图的矩阵区域及所属集合指针。

kind=9 新记录带 renderer_input_family、renderer_sources、renderer_storage / count / capacity。valid 2048=输入集合读取成功，4096=存储数组 header 满足受限校验；128 / 256 / 512 / 1024 分别为输出集合、源矩阵、输出矩阵、输出 owner 的读取结果。矩阵仍只覆盖 +0x70 开始的 128 字节。

`--renderer` 自测通过真实 MinHook trampoline 检查四参数转发、返回值、范围外仍调用原函数而不记录、构造结果采样、停止和原始入口恢复。相机、集合和副本自测同时通过。构建产物在 `tools/native-capture/build-renderer/GearsCaptureRenderer.dll`；五个原生入口在启动早期预留，并与两处 DXGI 入口一起接受停止后核验。

`analyze_renderer.py` 按 QPC 区间、线程、输入视图和输出地址关联嵌套的 kind=8 复制记录，不能用不同时间的同一地址冒充同一次构造。当前分析只接受观察到的单视图路径；多视图尚未验证。

## 重测中的启动日志问题

PID 41076 请求再次测试时，启动器曾短暂读取上次 PID 46420 的已完成日志，过早返回确认；新采样实际执行了 30 秒并正常停止，但未及时发出动作提示，不作为运动验证。原始数据另存 `renderer-original-41076.*`，不混入上表。

启动器现优先核对当前 PID 的命名采样事件；读取日志时要求文件更新时间改变且 capturing PID 一致。收集器新增 `--pid`，忽略旧进程的已完成状态；新增 `--summary` 只输出计数，完整报告仍写入本地文件。新 PID 43632 的实际启动返回确认了正确 PID 的采样事件，未误读前一轮日志。

## 已证明与剩余工作

已经观察到：原版和 Mod 下，输入 SceneView 经独立副本进入渲染器自己的集合与存储，owner 由输入集合改为输出集合，记录的矩阵保持一致。

这尚未证明构造后的实际渲染消费、对象销毁时机、第二眼所需状态、矩阵坐标约定或双目效果。下一步应跟踪集合在后续渲染执行路径的消费，再决定第二眼如何构造和输出；不直接把两个相同指针插入数组。
